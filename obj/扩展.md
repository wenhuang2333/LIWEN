## 0. 结论先行（TL;DR）

### 0.1 一句话结论

**不建议"换语言重写"，建议"按热点下沉 + 补齐缺失源码 + 换掉包装层"。**
当前功能的"不完全"主要来自四类不同原因，换语言只能解决其中一类：

| 缺陷类型 | 实例（本项目实测） | 正确解法 | 换语言有用吗 |
|---|---|---|---|
| **A. 依赖缺失导致的降级** | `pyaudio` 无 Python 3.14 wheel → 语音不可用；`lan_vpn.pyd` 不在仓库 → VPN 不可用 | 换可用的等价依赖 / 找回源码 | ❌ 无关 |
| 　└ *（v4.18.0 已解决）* | *语音改用 `sounddevice`；VPN 方案整体删除，改应用层组网* | *已落地* | *—* |
| **B. 平台能力未覆盖** | Windows 稀疏文件仍按表观大小统计（Python 不暴露 `st_blocks`）；Windows 扫盘未用 MFT | 调平台原生 API（`ctypes` 即可） | ❌ 无关 |
| **C. 协议/算法未做到工业级** | 语音裸 PCM 无 Opus；传输先整包压成临时 ZIP 再发；扫盘逐条 `stat` | 换算法/协议 | ⚠️ 部分 |
| **D. 单进程 Python 的并发上限** | GIL 限制多核压缩/哈希；7z 走 `py7zr` 纯 Python 路径 | 下沉到 Rust/C | ✅ 有关 |

**真正的 P0 不是语言，而是这三件事**：
1. ~~**`rust_/` 源码目录在本仓库不存在** —— `ui/vpn_page.py:84` 尝试 `import lan_vpn`，而 Rust 源码与其 `maturin` 构建链都不在版本库里。这是"功能不可用"的直接原因，也是**最大的可维护性风险**：一个二进制黑盒，没人能改、没人能重编、换台机器就消失。~~
   **（v4.18.0 已处置：VPN 方案整体删除，改用应用层组网；本项不再成立。）**
2. **PyQt6 是 GPLv3/商业双授权**，而本仓库**没有 `LICENSE` 文件**。若以二进制形式对外分发而不提供 GPL 源码，属于许可违规。PySide6（LGPLv3）是几乎零成本的替代（API 高度同源）。
3. **WebEngine 是安装包体积的决定性因素**（内嵌 Chromium，约 200 MB 量级），而它只服务于爬虫页的"可视化选择器"。是否值得为它付出 2/3 的体积，是个产品决策。

## 1. 现状盘点（先纠正一个前提）

### 1.1 "所有功能都是 Python 实现的"——不准确

事实是**混合栈，且混合方式最糟糕**：

| 组件 | 语言 | 在仓库中吗 |
|---|---|---|
| 全部 UI、核心逻辑、网络协议 | Python | ✅ 79 个文件 |
| ~~VPN 核心 `lan_vpn.pyd`~~ | ~~**Rust**~~ | ❌ ~~源码不在仓库~~ **（v4.18.0：VPN 方案已整体删除）** |
| ~~`wintun.dll`~~ | ~~C（上游 WireGuard 二进制）~~ | ~~✅ 427 KB，随仓库分发~~ **（v4.18.0：已删除）** |
| WebEngine/Chromium | C++（Qt 依赖） | ✅ 由 pip wheel 提供 |

**所以本项目并非"纯 Python"，而是"Python + 一个无法重建的 Rust 二进制黑盒"。**
问题的性质不是"Python 太慢"，而是"关键模块的源码丢失了"。

> **v4.18.0 更新**：那个"无法重建的 Rust 黑盒"**已随 VPN 方案一并删除**。现仓库是
> 纯 Python（联机走应用层组网），不再依赖任何无法重建的原生二进制。

### 1.2 依赖清单与降级现状（实测）

| 依赖 | 声明位置 | 实测状态 | 影响 |
|---|---|---|---|
| `PyQt6` / `PyQt6-WebEngine` | `requirements.txt` | ✅ 6.11.0 | UI 与爬虫内嵌浏览器 |
| `py7zr` / `pyzipper` / `pycryptodome` | 同上 | ✅ | 7z / ZIP-AES / 自研格式 |
| `requests` / `psutil` / `lxml` / `cssselect` / `beautifulsoup4` / `openpyxl` | 同上 | ✅ | 爬虫 / HTTP / AI / 网卡枚举 |
| `pyinstaller` / `Pillow` | 同上 | ✅ | 打包与图标生成 |
| ~~`pyaudio`~~ | ~~注释掉（可选）~~ | ✅ **已由 `sounddevice` 取代**（PyAudio 仅作回退） | ~~**语音通话完全不可用**~~ **（v4.18.0 已解决）** |
| ~~`lan_vpn`~~ | ~~不在 `requirements.txt`~~ | ❌ ~~无源码无产物~~ | ~~**VPN 隧道完全不可用**~~ **（v4.18.0：方案已删除，不再需要）** |
| `pytest` / `ruff` | 未声明 | ❌ | 无自动化测试与 lint 门禁（**仍未解决**） |

> **`pyaudio` 缺失的根因（已通过 PyPI API 实测确认）**：`PyAudio 0.2.14` 在 PyPI 上只有 **12 个 wheel，全部是 Windows（`win32`/`win_amd64`）**，标签仅覆盖 **cp38–cp313**。也就是说：
> - Python 3.14 → **无 wheel**（本项目实测踩中）；
> - **macOS / Linux → 从来就没有 wheel**，任何 Python 版本都必须本地编译 PortAudio。
>
> 对照 `sounddevice 0.5.6`：`py3-none-any` + macOS universal2 + `win32/win_amd64/win_arm64`，**Linux 与任何 Python 版本都能直接装**。
>
> 结论：**这不是"Python 不行"，而是"选错了库"**。`sounddevice` 是等价（同为 PortAudio 绑定）且分发友好得多的替代。
>
> **（v4.18.0 已落地）** `sounddevice` 已成为推荐后端并写入 `requirements.txt`，
> PyAudio 仅作自动回退，`voice_backend_name()` 只按"哪个库能 import"判断，
> 无 `sys.platform` 分支 —— 本问题**关闭**。

### 1.3 现状架构的一个优点（值得保留）

`core/` 目录**基本与 Qt 解耦**：`core/formats/`、`core/crawler/`、`core/compress.py`、`core/decompress.py`、`core/ai_client.py`、`core/http_client.py` 都是纯 Python、无 Qt 导入；Qt 只出现在 `core/workers.py`（QThread 包装）和 `core/file_index.py`（`ScanEngine` 一个 QThread 壳）。
**这意味着"无头核心 + 任意 UI 壳"的拆分在本项目里是低成本的**——`cli/` 已经证明了这条路可行（`main.py` 在 `len(sys.argv) > 1` 时不导入 Qt）。这是后面第 4 节混合架构建议的立足点。

> Python 保留在**编排层、IO 密集层、生态依赖层**（UI、爬虫、AI、HTTP、CLI、设置、安装器胶水）；

## 3. 逐功能语言/方式选型评估

### 3.1 压缩 / 解压

#### 3.1.1 ZIP
- **现状**：`zipfile`（deflate 走 C 的 zlib）+ `pyzipper`（AES 加密）。
- **瓶颈**：单线程；deflate 压缩率在现代标准下偏低。
- **候选**：

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| 保留 Python `zipfile`/`pyzipper` | 零成本、标准库稳定 | 单线程、无 zstd | ✅ **保留** |
| Rust `zip` crate（`aes-crypto` + `zstd` 特性） | 多核并行、可 zstd | 生态不如 Python 标准库"权威" | 可选 |
| libarchive（C，BSD） | 格式覆盖最广、久经考验 | 需 FFI | 备选 |

- **建议**：**保留 Python**。ZIP 不是本项目瓶颈，收益不足以支撑新构建环节。

#### 3.1.2 7z —— 唯一值得认真处理的格式
- **现状**：`py7zr`。它是"纯 Python 框架 + 少量 C 扩展（`pybcj`/`pyppmd`/`inflate64`）"，在**多核压缩**与**加密头/solid block/BCJ2** 上都不如原生实现。
- **为什么不能自己写**：7z 容器极其复杂（LZMA/LZMA2/PPMd/BCJ/BCJ2 过滤器链、solid 块、加密头、多卷、时间戳精度），自研必然在边缘用例上出错。
- **候选**：

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| 保留 `py7zr` | 已集成、纯 Python 易改 | 慢、边缘用例覆盖弱 | 作为回退保留 |
| **官方 `7z.dll`（LGPL）经 `ctypes` 调用** | 与 7-Zip 完全一致的兼容性、原生多核、支持加密头/多卷 | LGPL 分发需附许可与可替换说明；DLL 需随包分发 | ✅ **首选** |
| libarchive（C） | BSD 许可宽松、API 清晰 | 7z 写入能力弱于 7-Zip | 备选 |
| Rust `sevenz-rust2` | 纯 Rust 无 C 依赖 | 加密/多卷支持不如官方实现 | 观望 |

- **建议**：**P1**。7z 是用户最常遇到的"压缩慢/兼容报错"来源。推荐 **官方 `7z.dll` + Python 外壳**——**不需要换语言，只换后端**，`seven_z_handler.py` 的接口可以保持不变。
- ⚠️ 已知待修问题：`>999` 个 7z 分卷时 `multivolumefile` 的字典序排序会错乱（`v1000` 排在 `v999` 前）。这属于**算法缺陷，与语言无关**，任何后端都要显式处理。

#### 3.1.3 TAR / TAR.GZ / BZ2 / XZ
- **现状**：stdlib `tarfile`，压缩层是 C 的 zlib/bz2/lzma。
- **建议**：**保留 Python，不改**。瓶颈在压缩算法本身而非 Python。若要提速，唯一有效手段是"并行分块压缩"（pigz 思路），但会破坏 gzip 单流兼容性，不值得。

#### 3.1.4 自研 `.zhans` / `.shishan`
- **现状**：Python + `pycryptodome`（AES-256-GCM），含内容哈希去重（XOR filter）+ 逐文件 zlib 策略选择。
- **瓶颈**：逐文件 zlib 是**天然可并行**的任务，而 Python 受 GIL 限制只能用多进程（序列化开销大）或线程（GIL 下无收益）。
- **候选**：

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| 保留 Python | 零成本、算法已实现 | 多核吃不满 | ✅ 可保留 |
| **Rust 扩展（PyO3/maturin）** | `flate2`+`aes-gcm`+`rayon` 可吃满多核，预计 5–10× | 引入 Rust 构建链 | ✅ **P2 推荐** |
| C 扩展（手写 CPython API） | 无额外运行时 | 引用计数/异常处理易错 | ✗ 不推荐 |

- **建议**：**P2**。这是"自研格式"最有理由下沉的地方——因为**格式是你自己定的，没有兼容性包袱**，是最安全的 Rust 化试验田。

#### 3.1.5 压缩小结

```
ZIP  → 保留 Python          （收益低）
TAR  → 保留 Python          （瓶颈在算法）
7z   → 换后端：官方 7z.dll   （P1，收益高，不改语言）
zhans→ 下沉 Rust（PyO3）     （P2，最安全的 Rust 试验田）
```

### 3.2 空间索引 / 系统扫盘 —— **收益最高的单项**

#### 3.2.1 现状与已达成的水准
v4.17.0 已把扫盘重写为"层序同步 BFS + `ThreadPoolExecutor(4)` + 内存聚合 + SQLite `executemany` 批量写"，并修掉两个真实缺陷：
- **macOS firmlink 重复计数**（`/Users` 与 `/System/Volumes/Data/Users` 同 inode，实测 168,150 个重复目录）→ 按目录 inode 去重；
- **表观大小 ≠ 实际占用**（994 GB 磁盘报出 1896 GB）→ 改用 `st_blocks * 512`。

实测：`/Applications` 19.4 s → **9.7 s**（已等于纯遍历下限）；全盘 `/` **76.8 s**，851.63 GB vs 系统已用 831.29 GB（比值 1.024）。

#### 3.2.2 但"等于纯遍历下限"恰恰说明：算法已到天花板，**该换系统调用层了**
当前每次目录都要 `os.scandir` + 逐条 `stat`。**在 Windows 上，这条路径本身就比操作系统提供的能力慢两个数量级。**

#### 3.2.3 各平台的原生"快路径"

| 平台 | 现状（通用 API） | 原生快路径 | 预期收益 | 特权 |
|---|---|---|---|---|
| **Windows/NTFS** | `os.scandir` → `FindFirstFileW` 逐条 | **直接读 MFT**：`FSCTL_ENUM_USN_DATA` / `FSCTL_QUERY_USN_JOURNAL`，打开 `\\.\C:` 卷句柄 | **数十至数百倍**（分钟级 → 秒级） | 需管理员 |
| Windows（无管理员） | 同上 | `FindFirstFileExW` + `FindExInfoBasic` + `FIND_FIRST_EX_LARGE_FETCH`；`GetFileInformationByHandleEx(FileIdBothDirectoryInfo)` | 2–5× | 否 |
| **Windows 增量** | 全量重扫 | **USN Journal 增量**：只读变更记录 | 二次扫描接近瞬时 | 需管理员 |
| **macOS/APFS** | `os.scandir` + 逐条 `stat` | **`getattrlistbulk(2)`**：一次系统调用返回一整批目录项+属性（`du`/`fts` 内部就走这条） | 3–10× | 否 |
| **Linux** | `os.scandir` + `stat` | `getdents64` + **`statx(AT_STATX_DONT_SYNC)`**；高并发用 **`io_uring`** | 2–5× | 否 |

> **Windows 的 MFT 直读就是 WizTree / Everything 能在 1–2 秒扫完全盘的原因。** 本项目目前的能力与之相差两个数量级，且**这是纯系统调用差异，不是语言差异**。

#### 3.2.4 语言选型

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Python + `ctypes` 直接调 Win32/`getattrlistbulk`** | **不换语言**、不引入构建链、可逐步替换单层 | 需手写结构体/对齐；调试稍麻烦 | ✅ **首选（P0）** |
| Rust（`jwalk`+`rayon`）+ PyO3 | 更安全、多核更好、`windows` crate 有完整 Win32 绑定 | 引入 Rust 构建链 | ✅ 次选 |
| C/C++ 扩展 | 最快 | 手写 CPython API 风险高 | ✗ |
| 纯 Python 继续优化 | 无风险 | **已到天花板**，无空间 | ✗ |

**关键结论：扫盘提速 10–100× 完全不需要换语言。** `ctypes` 是标准库，`FSCTL_ENUM_USN_DATA` 是一个 `DeviceIoControl` 调用，`getattrlistbulk` 是一个 libc 调用。把 `file_index.py::_scan_one_dir()` 的"枚举"部分替换为平台快路径，SQLite 与 UI 层（`IndexDatabase`/`FileIndexModel`）完全不动。

#### 3.2.5 顺带修掉的 Windows 缺陷
Windows 上 Python 不暴露 `st_blocks`，导致稀疏文件（如 `Docker.raw`、虚拟磁盘）仍按表观大小虚增。
**修法**：`GetCompressedFileSizeW(path, &high)` 取实际分配大小，同样通过 `ctypes` 调用。**又是"不用换语言"的典型。**

#### 3.2.6 建议路线
```
P0-1  Windows: ctypes 读 MFT（管理员）+ FindFirstFileExW 回退（非管理员）
P0-2  Windows: GetCompressedFileSizeW 修稀疏文件虚增
P0-3  macOS:  getattrlistbulk 替换 os.scandir+stat
P1    Windows: USN Journal 增量扫描（二次扫描秒级）
P2    Linux:   statx + io_uring
```

### 3.3 局域网文件传输

#### 3.3.1 现状
`network/transfer.py`：TCP + 4 字节大端长度前缀 + JSON 元数据；**发送前把整包压成临时 ZIP，接收端解压后删除**。

#### 3.3.2 两个真实瓶颈
1. **临时 ZIP 造成二次磁盘 IO**：压缩 → 写盘 → 读盘 → 发送，对大文件是 2 倍多余磁盘吞吐，且首字节延迟 = 整个压缩时间。
2. **deflate 在现代硬件上性价比已落后**：zstd level 1–3 的压缩速度是 deflate 的 3–10×，压缩率相近甚至更好。

#### 3.3.3 候选

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **保留 Python + 流式 zstd + 分块并行** | 改造成本低、无新语言 | 单连接吞吐受限于线程/拷贝 | ✅ **首选（P1）** |
| Python `asyncio` + 多连接 | 无 GIL 阻塞、易做多流 | 现有代码是线程模型，需重写传输层 | 备选 |
| Rust `tokio` + `quinn`（QUIC） | 多流、0-RTT、天然并行 | 引入 Rust + 局域网 UDP 可能被防火墙拦 | P2 |
| Go `net` + goroutine | 部署简单 | 又引入一门语言 | ✗ |
| **`msquic`（Microsoft，C API）** | 工业级 QUIC、跨平台、可 `ctypes` 调 | API 复杂 | P2 观望 |

#### 3.3.4 建议
**P1：保留 Python，做三件事即可拿到大部分收益**——
1. 用 `zstandard`（有官方 wheel，C 扩展，**释放 GIL**）做**流式**压缩，去掉临时 ZIP 文件；
2. 大文件按块（如 4–8 MB）用 `ThreadPoolExecutor` 并行压缩，因为 zstd 扩展在压缩时释放 GIL；
3. 发送端零拷贝思路：`socket.sendfile()`（Linux/macOS）或加大 SO_SNDBUF。

**不需要换语言。** 只有当需要"多连接聚合跑满 10GbE"时，才值得考虑 Rust/QUIC。

## 4. Windows UI App 的实现方式

> 你的前提是"允许保留 Python + Qt"。**我的结论是：短期应当保留 PyQt（但建议迁到 PySide6），中期再考虑换壳。** 下面把所有可行路线摊开对比。

### 4.1 四种架构形态

| 形态 | 机制 | 代表 | 适合 |
|---|---|---|---|
| **① 脚本 + 打包器** | Python 解释器 + 依赖打进一个目录/exe | PyInstaller、Nuitka、cx_Freeze、py2app、Briefcase | 快速交付、团队只有 Python |
| **② 托管语言原生 UI** | 编译型运行时 + 系统 UI 框架 | C# WinUI3/WPF/Avalonia、C++ Qt、Delphi | 追求原生观感与启动速度 |
| **③ 系统 WebView 壳** | 原生窗口 + 系统浏览器内核 + Web 前端 | Tauri、Wails、Electron、PyWebView | 前端技能强、要小体积 |
| **④ 编译型 GUI 框架** | 直接绘制，无 WebView | Rust egui/iced/Slint、Flutter、Dear ImGui | 极致体积/启动、愿意学新框架 |

### 4.2 保留 Python + Qt 路线（现状路线的优化）

| 框架 | 许可 | 说明 |
|---|---|---|
| **PyQt6（现状）** | **GPLv3 / 商业双授权** | 功能最全、文档最多；**闭源分发需购买商业许可** |
| **PySide6** | **LGPLv3** | Qt 官方绑定，API 与 PyQt6 高度同源，**闭源分发免费** |

**强烈建议：迁到 PySide6。** 理由：API 同源、迁移机械（见下表）、解掉许可风险、获得 Qt 官方长期支持。

PyQt6 → PySide6 的主要差异（全部是机械替换）：

| PyQt6 | PySide6 |
|---|---|
| `pyqtSignal` / `pyqtSlot` | `Signal` / `Slot` |
| `from PyQt6.QtCore import ...` | `from PySide6.QtCore import ...` |
| `app.exec()` | `app.exec()`（相同） |
| `QWebChannel` 用法细节 | `QtWebChannel`，注册方式略异 |

### 4.5 混合架构：Python 核心 + 原生壳（本项目最优解）

因为 `core/` 已经基本与 Qt 解耦（见 §1.3），**"无头核心 + 任意壳"在本项目是低成本的**。三种接法：

| 接法 | 机制 | 优势 | 劣势 | 适合本项目？ |
|---|---|---|---|---|
| **A. 子进程 + JSON-RPC/stdio** | 壳启动 `python core_daemon.py`，按行 JSON 通信 | 语言/进程隔离干净；核心可崩溃重启；壳可用任意语言 | 需定义协议；启动多一个进程 | ✅ **推荐** |
| **B. 本地 HTTP 服务** | 核心监听 `127.0.0.1:<随机端口>` + token 鉴权 | 调试方便（curl 即可）；天然支持 Web 前端（Tauri/Wails） | 需处理端口占用与鉴权安全 | ✅ 推荐（尤其配 Tauri） |
| **C. 嵌入式解释器 / PyO3** | 壳内嵌 Python（`pyo3`、`pythonnet`）或 Python 内嵌 Rust（`maturin`） | 无 IPC 开销 | **构建与分发最复杂**、GIL 交互、崩溃会拖垮整个进程 | ⚠️ 仅"Python 调 Rust 扩展"这一方向推荐 |
| **D. 纯 C ABI cdylib** | 核心编译成 `.dll`/`.so`，壳用 `ctypes`/P/Invoke 调用 | 无 IPC、无 Python 依赖 | 接口面窄（只适合函数级 API） | ⚠️ 仅适合计算热点 |

**推荐组合**：
- 想保留 Python 全部能力 + 换小体积 UI → **Tauri v2 壳 + Python sidecar（方案 A/B）**；
- 想全 Rust → **Slint/egui 壳 + `liwencore`（Rust cdylib）+ 可选 Python sidecar 仅供爬虫/AI**；
- 想 Windows-only 最佳观感 → **WinUI 3 壳 + 核心通过命名管道/stdio 通信**。

### 4.6 针对本项目的 UI 建议（分阶段）

| 阶段 | UI 方案 | 触发条件 |
|---|---|---|
| **现在** | **PyQt6 保留**，但**迁 PySide6** 解许可风险 | 立即（成本低、收益明确） |
| 短期 | PyQt6/PySide6 + **Nuitka 评估** + **WebEngine 可选化** | 体积/启动成为用户抱怨点 |
| 中期 | **Tauri v2 壳 + Python sidecar**，或 **Slint** 纯 Rust 壳 | 需要把安装包从数百 MB 降到 <20 MB |
| 长期 | **WinUI 3**（若确定 Windows-only）或 **Avalonia**（若需跨平台 .NET） | 团队技术栈转向 .NET |

**不建议**：Electron（体积比现在更差）、Kivy/Dear PyGui（观感不符消费级桌面）、Win32/MFC（开发成本不划算）。

## 7. 风险、坑与不建议的做法

### 7.1 许可风险（**当前已存在**）
| 组件 | 许可 | 风险 |
|---|---|---|
| **PyQt6** | GPLv3 / 商业 | 闭源分发**必须**购买商业许可，或以 GPL 提供源码。**建议迁 PySide6（LGPL）** |
| PySide6 | LGPLv3 | 闭源可分发（需允许替换该库） |
| **仓库无 `LICENSE` 文件** | — | 默认"保留所有权利"，他人无法合法使用/贡献 |
| `7z.dll` | LGPL + unRAR 限制 | 分发需附许可与可替换说明 |
| ~~`wintun.dll`~~ | ~~MIT / Apache-2.0 双许可~~ | **已删除（v4.18.0），不再涉及** |
| libarchive | BSD | ✅ 宽松 |

### 7.2 技术风险
1. **同时维护两套 UI 是灾难**。要么全 PySide6，要么全 Tauri，**不要 Python 壳 + 原生壳并行**。
2. **PyInstaller 杀软误报**：`onedir` 明显优于 `onefile`；代码签名可大幅缓解。
3. **Python 3.14 生态滞后**：本次已实测踩坑（`pyaudio`）—— 该具体问题已由 `sounddevice` 解决（v4.18.0）。建议仍锁 3.12/3.13。
4. **交叉编译陷阱**：macOS 交叉编译 Windows 时，MSVC 运行时、架构、签名都要单独处理；**最稳的是原生 Windows CI runner**。（原举例的 `wintun.dll` 已随 VPN 方案删除，不再是交叉编译负担。）
5. **数据/设置向后兼容**：`settings.json`、`rooms.json`、`space_index_*.db` 都有既定格式，任何重构都必须做迁移，**不能静默丢用户数据**。
6. **不要为了"语言更现代"而重写爬虫/AI/HTTP/CLI** —— 这些是 Python 生态优势区，重写是纯亏损。
7. **MFT/USN 直读需要管理员**：必须保留"非管理员回退路径"，否则普通用户反而更慢。
8. **MSIX 沙箱与"扫盘"天然冲突**：若考虑 Store 分发，需先验证文件系统访问权限。

### 7.3 明确"不建议"的选项
| 选项 | 理由 |
|---|---|
| 全量重写为 Rust/C++ | 29,343 行、16 个线程类、大量平台适配，重写风险远超收益 |
| 换 Electron | 体积比现状更差 |
| Kivy / Dear PyGui 做消费级桌面 | 观感不符 |
| 自研 7z / VPN 协议 | 格式与协议复杂度极高，应复用成熟实现 |
| Python 里手写 C 扩展（CPython API） | 引用计数与异常处理易错，应走 PyO3 |
| 保留 PyQt6 而不处理许可 | 法律风险 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| **MFT** | Master File Table，NTFS 的中央文件元数据表。直读它可在数秒内枚举全盘 |
| **USN Journal** | Update Sequence Number Journal，NTFS 的变更日志，用于增量扫描 |
| **`getattrlistbulk`** | macOS 批量取目录项+属性的系统调用，`du`/`fts` 的内核加速路径 |
| **`statx`** | Linux 的扩展 `stat`，支持 `AT_STATX_DONT_SYNC` 避免同步 IO |
| **firmlink** | macOS 上把 `/System/Volumes/Data/...` 映射到 `/...` 的机制，会导致重复枚举 |
| **PyO3 / maturin** | Rust 与 Python 互操作的库 / 构建工具，用于产出 `.pyd`/`.so` 扩展 |
| **cdylib** | Rust 编译产物类型，输出 C ABI 动态库 |
| **AEC / PLC / FEC** | 回声消除 / 丢包隐藏 / 前向纠错，语音质量的三个关键机制 |
| **sidecar** | 由主程序管理的伴随子进程（如 Tauri 壳旁的 Python 核心进程） |
| **onedir / onefile** | PyInstaller 的两种打包形态：目录式（启动快、误报低）/ 单文件（自解压、启动慢） |
