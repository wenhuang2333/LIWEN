## 1. 项目定位

**帽兜工具**（英文名 **LIWEN Tool**，早期内部代号 ArchiveTool / MaoDou）是一款基于 **PyQt6** 的跨平台桌面工具集，
主要面向 Windows 用户，通过 PyInstaller 打包为独立 `.exe`。

它把「压缩解压 / 局域网传输 / 局域网联机（应用层组网：广播发现 / 直连加入 / 语音 / 房间内文件传输）/ 可视化爬虫 / HTTP 请求调试 /
多模型 AI 对话 / 磁盘空间分析 / 故障自检与修复」整合在一个统一的深色（Catppuccin Mocha 风格）界面中。

| 项 | 值 |
|---|---|
| 语言 | Python 3.10+（当前开发环境 3.14.5） |
| GUI 框架 | PyQt6 + PyQt6-WebEngine |
| 界面风格 | Fusion + 动态生成 QSS（主题强调色可配） |
| 打包 | PyInstaller（onedir / onefile） |
| 版本号来源 | `code/utils/constants.py` → `APP_VERSION`（`ui/about_page.py` 再导出） |
| 窗口标题 | 帽兜工具 |

### 为什么这些文件必须留在根目录

| 文件/目录 | 原因 |
|---|---|
| `.venv/` | 虚拟环境内部记录绝对路径（`pyvenv.cfg`、`bin/activate`），移动即失效 |
| `.idea/`、`.claude/` | 工具链按约定在项目根读取配置 |
| `CLAUDE.md` | Claude Code 只在项目根查找该文件 |
| `requirements.txt` | 依赖清单惯例位置，`pip install -r requirements.txt` 直接可用 |
| `dist/`、`build/` | 构建脚本的固定输出位置 |

## 3. 环境准备与运行

### 3.1 安装依赖

```bash
pip install -r requirements.txt
```

依赖清单：`PyQt6`、`PyQt6-WebEngine`、`py7zr`、`pyzipper`、`pyinstaller`、
`pycryptodome`、`lxml`、`cssselect`、`beautifulsoup4`、`openpyxl`、`requests`、
`psutil`、`Pillow`、`sounddevice`。

可选依赖（缺失时功能优雅降级，不影响启动）：

| 依赖 | 用途 | 缺失表现 |
|---|---|---|
| `sounddevice`（推荐）/ `pyaudio`（回退） | 联机语音通话 | 语音按钮禁用，检测页给出「安装音频后端」修复项；房间其余功能不受影响 |
| `psutil` | 更准确的网卡枚举 | 回退到 socket 实现 |

> **联机（房间）本身没有任何可选原生依赖**：协议层只用标准库
> （`socket` / `threading` / `json`）+ PyQt6，不需要驱动、不需要管理员，
> 三平台共用同一套代码。

### 3.2 运行方式

```bash
# GUI 模式（从项目根目录执行；无参数即 GUI）
python code/main.py

# CLI 模式（任何参数都会进入 CLI，且不会导入 Qt，启动更快）
python code/main.py --help
python code/main.py settings-list
python code/main.py compress ./src -o out.zip -f zip -l 0
python code/main.py decompress out.zip -d ./out
```

> **关键机制**：`python code/main.py` 会把 `code/` 加入 `sys.path[0]`，
> 因此 `ui/`、`core/`、`utils/` 等包名保持不变，内部 `from core.xxx import ...`
> 这类绝对导入**无需改写**。这也是把入口脚本放在 `code/` 内的原因。

### 3.3 使用虚拟环境运行（推荐）

```bash
# macOS / Linux
.venv/bin/python code/main.py

# Windows
.venv\Scripts\python.exe code\main.py
```

## 4. 架构分层

```
                    ┌──────────────────────────────┐
                    │  code/main.py                │
                    │  无参数 → GUI / 有参数 → CLI │
                    └───────┬──────────────┬───────┘
                            │              │
                 ┌──────────▼───┐   ┌──────▼────────┐
                 │  ui/         │   │  cli/         │
                 │  PyQt6 页面  │   │  argparse     │
                 └──────┬───────┘   └──────┬────────┘
                        │                  │
                 ┌──────▼──────────────────▼───────┐
                 │  core/   业务核心（与界面无关）  │
                 │   ├ formats/  归档格式插件层     │
                 │   ├ crawler/  爬虫引擎           │
                 │   ├ workers.py QThread 任务      │
                 │   └ file_index / ai_client ...   │
                 └──────┬──────────────────────────┘
                        │
          ┌─────────────▼────────────┐   ┌──────────────────┐
          │  network/  传输·房间·语音 │   │  utils/ 配置·日志 │
          └──────────────────────────┘   │  ·路径·常量       │
                                         └──────────────────┘
```

### 4.1 依赖方向（务必遵守）

- `ui/` 可以依赖 `core/`、`network/`、`utils/`
- `core/` 的**纯逻辑部分不得 import PyQt**（`formats/`、`crawler/`、`ai_client.py`、`http_client.py`）
  - 例外：`core/workers.py`、`core/file_index.py` 提供 QThread 封装，属于 Qt 适配层
- `network/` 不得依赖 `ui/`
- `utils/paths.py` 是**叶子模块**，不得 import 其它项目模块（避免循环依赖）

### 4.2 入口与启动顺序（`code/main.py`）

启动顺序有强约束，改动时需注意：

1. `settings.load()` —— 必须最先执行，因为主题强调色来自设置
2. `setup_logging()` —— 打开 `data/log.txt`
3. 创建 `QApplication`，设置 Fusion 风格
4. `install_crash_handler()` —— 安装全局异常钩子（弹窗 + 记录堆栈）
5. `MainWindow()` → `show()` → `app.exec()`

CLI 分支则在 `_setup_console()`（仅 Windows，用于 windowed 打包时输出到父控制台）
之后调用 `cli.run_cli(sys.argv[1:])`。

## 6. 路径解析规范（本次重构的核心）

### 6.1 问题背景

整理前，代码散落着大量这种写法：

```python
os.path.dirname(os.path.dirname(os.path.abspath(__file__)))   # 猜"项目根"
```

它**依赖文件的目录深度**。一旦源码从根目录搬进 `code/`，这些表达式会静默地
指向 `code/` 而不是项目根，导致图标找不到、日志写到错误位置、数据库路径漂移——
**不会报错，只会行为异常**。这是最危险的一类重构副作用。

### 6.2 解决方案

新增 `code/utils/paths.py`，作为全项目唯一的路径来源：

| 函数 | 返回 |
|---|---|
| `project_root()` / `app_dir()` | 源码运行 → 项目根；冻结运行 → exe 所在目录 |
| `CODE_DIR` / `PROJECT_ROOT` | 常量形式 |
| `static_dir()` / `static_path(*parts)` | `static/`（冻结时 `sys._MEIPASS/static`） |
| `data_dir(create=False)` | `data/` 运行时可写目录 |
| `dist_dir()` / `project_path(*parts)` | `dist/`、项目根拼接 |
| `is_frozen()` | 是否 PyInstaller 打包运行 |

### 6.3 使用约定

```python
# ✅ 正确
from utils.paths import static_path, data_dir, project_root
icon = static_path("logo.jpg")
db   = os.path.join(data_dir(), "space_index_C.db")
cwd  = project_root()

# ❌ 禁止
icon = os.path.join(os.path.dirname(os.path.dirname(__file__)), "static", "logo.jpg")
```

**例外**：`code/installer/` 下的脚本常被用户**单独执行**
（如 `python code/installer/right_menu.py install`），此时 `code/` 不在 `sys.path` 中，
无法 `import utils.paths`，因此这几个文件保留了显式的三级 `dirname()` 并附带注释说明。

## 9. 线程模型

**所有耗时操作必须在 `QThread` 子类中执行，禁止阻塞主线程。**
全部 worker 集中在 `code/core/workers.py`。

约定的交互方式：

- 通过 `pyqtSignal` 向 UI 回报进度 / 日志 / 结果
- 通过回调（`progress_callback`）向纯逻辑层传递进度
- 需要用户确认时，用 `threading.Event` 跨线程同步：
  worker 发信号 → 主线程弹 `QMessageBox` → 主线程写回决策并 `event.set()` 解除阻塞
- 取消通过布尔标志 + `requestInterruption()` 实现

**例外**：`CrawlerPage` 自行管理 `CrawlWorker` / `SiteCheckWorker` 的生命周期，
`MainWindow` 不介入。

### 11.2.1 联机（房间）的架构与验证（v4.18.0）

**联机走纯应用层组网，不打包任何平台专有二进制。** 此前基于 TUN 的「VPN 隧道」方案
（Rust `lan_vpn` + `wintun.dll` + UAC 提权 + `ui/vpn_page.py`）已**整体删除**，因此：

- 仓库根目录**不再有任何 Windows 专有二进制**（原 `wintun.dll` 已删除）；
- `build.py` **不打包任何驱动**，`--uac-admin` 已移除（应用本体不需要管理员权限），
  `hidden_imports` 中的音频后端是 `sounddevice`；
- 联机路径上**没有 `sys.platform` 分支、没有原生模块、没有驱动、没有管理员要求**，
  Windows / macOS / Linux 共用同一套代码，可跨平台混合联机。

**加入房间的两条路径**（最终都走同一套 TCP 挑战-应答流程）：

| 路径 | 机制 | 适用场景 |
|---|---|---|
| 广播发现 | 房主 UDP 12347 广播房间公告，`RoomDiscoveryClient.scan_rooms()` 收集 | 同一局域网 |
| **直连加入** | `RoomJoinClient.probe_room(host_ip, port)` 向房间的加入端口发 `MSG_ROOM_PROBE` 取回「房间名片」，再用其中的 `room_id` 正常加入 | 跨网段、广播被 AP 隔离 |

「房间名片」的字段与 UDP 广播公告**完全相同**（`room_id` / `room_name` / `host` /
`username` / `port` / `need_password` …），**绝不包含 `session_id`** —— 它是房主签发的
会话凭证，泄漏给同房间其他成员即可冒充他人。CLI 上 `room-join --room-id` 因此变为
可省略（缺省时自动探测），并新增 `room-probe`。

**端口推导**（一律由房间端口算出，所有参与者结果一致，无需额外协商）：

| 用途 | 端口 | 推导来源 |
|---|---|---|
| 房间公告 / 发现 | UDP 12347 | `ROOM_DISCOVERY_PORT` |
| 加入服务 / 直连探测 | TCP `room_port + 1`（默认 12346） | `RoomHost` / `RoomJoinClient._join_target()` |
| 语音 | UDP 12400–12799 | `utils.constants.voice_port_for_room()` |
| 房间内文件传输 | TCP 12800–13199（默认 12345 → 13160） | `utils.constants.room_data_port_for_room()` |

> `VOICE_PORT_OFFSET` 已从 `utils/constants.py` 删除 —— 语音端口**不允许**再写成
> `room_port + N`（默认端口下 `+2` 正好撞上 12347 房间发现端口）。
> `room_data_port_for_room()` 推导时会跳过 12345 / 12346 / 12347、房间端口、
> 房间端口 + 1 与该房间的语音端口。

**跨平台验证脚本** `code/tools/verify_multiplayer.py`（取代已删除的 Windows 专属
`diagnose_vpn.py`）：

| 命令 | 作用 |
|---|---|
| `python code/tools/verify_multiplayer.py` | 默认 36 项：房间创建 → 广播发现 → 直连探测 → **畸形 room_id / 非 JSON 对象应答不崩溃** → **空 peer_id 不泄漏 session_id** → 挑战-应答加入 → 心跳与名单 → 会话失效 → 房间内文件传输 → 音频后端可用性 → 语音关闭时序（含 exit 139 段错误回归） |
| `python code/tools/verify_multiplayer.py --gui` | 追加 7 项（合计 43）：离屏 Qt 跑通联机大厅「直连加入」整条链路（大厅 → 探测 → 加入 → 房间视图 → 离开回大厅） |
| `python code/tools/verify_multiplayer.py --audio` | 额外 3 项（合计 39）：实测「音频设备能否打开」（会触发系统麦克风授权弹窗）+ 「从不 stop() 也干净退出」 |
| `python code/tools/fuzz_multiplayer.py` | 对抗性/不变量测试 15 项：A 端口推导穷举 6.5 万组 / B 103 组畸形 TCP 应答 / C 畸形 UDP 报文 / D 房主广播抗畸形包 / E 畸形心跳名单 / F 人数上限 / G `ping_host` / H 资源泄漏 / I `_recv_header` 边界。**不可与 verify 脚本同时运行**（都要占 UDP 12347） |

脚本纯跨平台、**无需管理员**，任何平台都能跑；音频不可用时按预期降级并如实报
`FAIL` / `SKIP`，不假装成功。

## 12. 编码规范

### 12.1 跨平台硬性要求

1. **系统调用必须用 `sys.platform` 守卫**：`"win32"` / `"darwin"` / 其它视为 Linux
2. **使用跨平台助手**：
   - `utils.helpers.open_file_or_dir()` 代替 `os.startfile()`
   - `utils.helpers.spawn_detached()` 代替裸 `subprocess` 平台常量
   - `utils.repair_helpers._find_executable()` 做可执行文件发现
3. **禁止硬编码路径**（`C:\`、`Program Files`、`%APPDATA%`），一律走 `utils.settings._get_app_data_dir()` 或 `utils.paths`
4. **禁止硬编码扩展名**：`.exe` 仅 Windows 使用，走 `utils.repair_helpers._EXE_SUFFIX`
5. **禁止硬编码字体**：等宽字体用 `ui.styles.MONO_FONT_FAMILY`
6. **禁止 `encoding="gbk"`**：子进程输出用 `locale.getpreferredencoding()`
7. **平台专属功能必须优雅降级**：右键菜单（`installer/right_menu.py`）、
   Windows 安装程序（`installer/`）在其它平台必须给出「当前平台不支持」提示，不得崩溃。
   **注意：联机（房间）不属于平台专属功能** —— 它必须三平台完全一致，
   不得引入任何 `sys.platform` 分支、虚拟网卡或管理员要求
8. **新增文件读写一律通过 `utils/paths.py`**

### 12.2 日志要求

每个函数/功能都应记录执行情况到 `data/log.txt`：

- `info()` —— 进入/退出关键流程
- `warn()` —— 可恢复的异常
- `error()` —— 失败
- `utils.logger.function_scope(name)` —— 函数级进入/退出上下文管理器

未捕获异常由 `install_crash_handler()` 记录完整堆栈并弹窗提示。

## 14. 常见问题

**Q：为什么运行报 `ModuleNotFoundError: No module named 'ui'`？**
A：入口必须在 `code/` 内执行，即 `python code/main.py`。
从项目根执行 `python main.py` 已不再适用（该文件已不存在）。

A：运行日志现位于 `data/log.txt`。目录不存在时程序会自动创建。

**Q：`data/` 可以删吗？**
A：可以，整体删除即可。程序会重建，代价是空间索引需要重新扫描。

A：检查 `static/` 是否完整，且 `utils/paths.py` 未被改动。
可运行 `python -c "from utils.paths import static_path; import os; print(static_path('logo.jpg'), os.path.exists(static_path('logo.jpg')))"`（在 `code/` 下执行）。

A：这是「专有压缩刻度」的设计行为——等级 > 0 时会被包进 `.zhans` 容器。

## 15. 稳定性与安全性优化记录（v4.16.1）

本轮为「不改功能、只修缺陷」的加固。全部改动都经过可复现的实测验证，
不改动任何磁盘格式与网络线协议。

### 15.1 启动与持久化

| 问题 | 现象 | 处理 |
|---|---|---|
| `utils/settings.py` 在 **import 期**写盘 | 无写权限时 `import` 直接抛 `PermissionError`，程序无法启动；`HOME` 只读即可复现 `IMPORT CRASH` | 改为惰性保存；新增 `_is_writable_dir()` 与 `_resolve_settings_dir()`，按 `应用数据目录 → ~/.liwentool → /tmp/LIWENTool` 逐级降级并置 `_SETTINGS_DIR_DEGRADED` |
| JSON 写入非原子 | 崩溃/断电时 `settings.json`、`rooms.json` 等被截断成空文件，配置全部丢失 | 新增 `code/utils/jsonstore.py`：`mkstemp` 同目录临时文件 → `flush` + `fsync` → `os.replace`，全程加锁且**永不抛异常**（只记日志） |
| 全局异常与线程异常无记录 | 子线程里的异常静默消失 | `utils/logger.py`：`threading.excepthook` + `faulthandler`；崩溃对话框通过 `QueuedConnection` 投递回 GUI 线程（原实现在工作线程建 `QMessageBox`） |

### 15.2 打包

`static/logo.ico` 此前是一个**改名后的 PNG**（与 `logo.jpg` 字节仅同名不同），
PyInstaller 会打包出一个无效图标。`code/build.py` 现会校验 ICO 魔数
（`00 00 01 00`），必要时重新生成真正的方形多尺寸 ICO（16/32/48/64/128/256），
并额外产出 macOS/Linux 需要的 `logo.png`。`requirements.txt` 补齐了此前未声明的
`psutil`（网卡枚举）与 `Pillow`（图标生成）。

### 15.3 设备发现（`开始监听` 曾完全不可用）

- `code/network/discovery.py` 只定义了 `DiscoveryService`，但
  `ui/main_window.py`、`ui/diagnostic_page.py` 三处引用了**不存在的**
  `DeviceDiscovery` → 点击「开始监听」抛 `ImportError`（弹崩溃框，而接收线程
  仍在跑），「手动扫描」则永远返回 0 个设备。现统一改用 `get_discovery_service()`。
- `reply_listener()` 是阻塞调用（默认 3 s），此前直接在 `QTimer` 回调里执行 →
  **每 4 秒界面卡死 3 秒**（实测 3.01 s）。现移入 `_ReplyListenerThread`。
- 新增 `scan_now(timeout)` 供扫描与诊断使用；`set_listen_port()` 让应答里带上
  真实接收端口（原先固定上报 12345）。
- 回调列表加锁并遍历快照，避免扫描线程与 GUI 线程并发改列表。

### 15.4 归档层

| 问题 | 说明 |
|---|---|
| **解压路径穿越** | `custom_handler` / `shishan_handler` 直接用条目名拼路径，`../x`、`a/../../x`、`/abs/x` 均可写到目标目录之外（已实测复现）。现统一经 `_safe_join()`（`realpath` + 前缀校验） |
| **解压炸弹** | 2 MB 压缩包声明 2 GB 可把峰值内存推到 **~2.9 GB**。现改用 `zlib.decompressobj` 流式解压并硬性限制在声明大小；实测 65 KB → 64 MB 展开时 **RSS 零增长** |
| tar 系解压完全不可用 | `tar.extract(..., filter="data")` 仅 Python 3.12+ 支持，3.10/3.11 直接 `TypeError`。新增 `_base.tar_extract()` 按版本分支，并在老版本上手工做同强度校验（含 Windows 盘符，跨平台判定） |
| 损坏包报 `struct.error` | 目录表越界解包、坏字节 `decode` 都会把原始异常抛给用户。现全部前置边界检查，抛出中文 `ValueError`，并统一用 `errors="surrogateescape"` |
| 压缩失败毁掉旧归档 | 中途失败会留下截断的坏文件、覆盖用户原有压缩包。现一律写 `*.part`，成功后 `os.replace()`，失败清理 |
| 成功后却没有文件 | ZIP/7z 对不存在或空的输入返回"成功"（大小 0、文件数 0）。现在 `FileNotFoundError` 明确点名缺失路径 |
| ZIP 读取逻辑混乱 | 通配 `except Exception: pass` 把"密码正确但包损坏"误报为密码错误；`extract_single` 无法读自己写的 AES 包。现一次性选定 reader、分类翻译异常 |
| 7z 分卷是假的 | `volume_size` 被静默忽略、`supports_volumes()` 却返回 `True`，UI 还提供分卷控件。现用 `multivolumefile` **真正实现**分卷读写（`.7z.001` 命名） |
| 进度回调过密 | 2000 个文件产生 **正好 2000 次**跨线程 Qt 信号，界面卡死。现按"整数百分比变化 + ≥0.1 s 间隔"节流并保证收尾 100%（实测 2000 → 2 次） |

### 15.5 网络传输（`network/transfer.py`）

多文件发送此前只传第一个文件；长度前缀只 `recv` 一次，TCP 分包即损坏；
包头无上限（可被诱导分配巨量内存）；截断被当成成功；未校验的 JSON 元数据直接使用；
自动解压可被 zip 炸弹撑爆磁盘；处理线程无上限。现分别修正为：
循环发送全部文件、`recv_exact()` 收全、`MAX_HEADER_SIZE = 64 KB`、
`received != size` 即判失败并删除 `.part`、字段逐一校验、
`MAX_RECV_BYTES = 64 GiB` 与 `BoundedSemaphore(MAX_CONCURRENT_HANDLERS)`。
重复文件名自动去重（`a.bin` → `a (1).bin`）。

### 15.6 联机房间与语音

- **心跳从未被处理**：`_handle_join` 只在 `type == room_join_request` 时才认，
  而客户端周期发的是 `heartbeat` → 每个成员在 `HEARTBEAT_TIMEOUT`(10 s) 后
  都被当成离线剔除，大厅人数**永远掉回 1**。现识别心跳、刷新 `last_heartbeat`
  并回 `heartbeat_ack`（实测持续 14 s 心跳后人数稳定）。
- `max_players` 从未生效 → 现真正限制（房主占 1 席）。
- 口令比较改用 `hmac.compare_digest()`（常量时间）。
- 房间端口越界时 `bind()` 抛 `OverflowError`（未被捕获）会让 join 线程静默死亡；
  `join_room()` 对广播来的端口先做范围校验。
- **语音端口冲突**：语音端口原为 `room_port + 2`，默认端口下正好是
  **12347 = 房间发现端口**，而房主已占用该 UDP 端口 → **房主侧语音永远起不来**，
  却仍提示"语音已连接"（`start()` 早已返回 True）。现新增
  `utils.constants.voice_port_for_room()` 从专用区间取端口，并让 `start()` 在
  bind / 打开音频设备失败时**如实返回 False**。
- 播放线程用 `settimeout(0.05)` 却每轮只播一帧（20 ms）→ 播放速率被压到
  20 帧/秒（采集 50 帧/秒），约 **84% 音频被丢弃**。现改非阻塞收包 + 固定 20 ms
  节拍播放，并带落后补偿（实测播放比例 ~130%，即已跟上采集速率）。
- 抖动缓冲与序号表增加对端数量上限，序号表随队列一起回收（原会无界增长）。

### 15.7 界面线程模型

- `SpaceScanWorker.run()` 原先**没有 try/except**，异常逃出 `run()` 后页面永远
  收不到 `finished`/`error`，进度条卡死；取消路径在活线程上 `disconnect()` 并置
  `None`，紧接着重新扫描会关掉旧连接、删库、建新库，正在写的线程随即抛
  `sqlite3.ProgrammingError`。现：`run()` 全包 try/except 并 `emit(error)`，
  新增 `_release_worker()`（取消 → `wait` → 逐个断信号），活线程绝不丢引用；
  新增看门狗 `_check_scan_health()` 兜底复位。
- 爬虫：停止后立刻重开会话时，旧任务的终止信号会把**新任务**置为空闲状态
  （停止按钮失效、两次数据混在一起）。现所有终止槽用 `self.sender()` 守卫，
  旧 worker 进入 `_retired_workers` 由定时器回收；GUI 线程不再出现阻塞式
  `wait()`（唯一残留的 `wait` 在 `cleanup()`，带统一 deadline）。
- 数据表渲染上限 `_MAX_TABLE_ROWS = 2000`，导出数据仍完整保留（实测 5000 行输入
  → 表格 2000 行、RSS 仅 +4 MB）。
- `HttpRequestPage.cleanup()` 对默认 30 s 超时的请求只等 3 s 就返回，线程仍在跑；
  现统一为 `_CLEANUP_WAIT_MS = 8000`，先断信号再等待，超时保留引用而非
  `terminate()`。
- 预览对话框：`list_contents()` 现在会为损坏包抛错，`archive_preview_dialog`
  与 `main_window._open_preview` 均已捕获并给出中文提示（原先会冒到全局崩溃框）。
- `lan_page` 新增 `set_scan_busy()` / `set_ping_busy()`，重复点击不再产生并发线程。

### 15.8 其它

- `network/interfaces.py` 的 `_is_valid_ip()` 原先强制 `is_private`，会漏掉
  **CGNAT 100.64/10**（校园网/热点常见）与机构内网直连公网段。现改为排除法：
  只剔除回环、链路本地、未指定、组播、保留地址。
- `core/file_index.py` 的 CLI 路径会复用旧数据库，导致已删除文件的**幽灵条目**
  与目录大小重复累加。新增 `IndexDatabase.clear()`，扫描开始即清空，并以
  `scan_meta.scan_complete` 标记快照是否完整（取消/异常为 `0`）。
- `diagnostic_page` 的损坏索引库检查在 `try` 内部 `conn.close()`，查询异常时
  连接泄漏（Windows 上文件被占，随后删不掉）。
- 移除两处违反项目规范的 `encoding="gbk"`（`ui/vpn_page.py`、`diagnose_vpn.py` ——
  两个文件均已于 v4.18.0 随 VPN 方案删除，此处仅记录当时的修复），
  改用 `locale.getpreferredencoding()` 并在中文 Windows 上回退到 OEM 代码页。
- `build.py` 写 `.app` 的 launcher / `Info.plist` 时显式 `encoding="utf-8"`
  （内容含中文应用名，Windows 上会用 ANSI 代码页导致元数据乱码）。

| 问题 | 实测证据 | 处理 |

| **macOS 固件链接重复计数** | `/` 是 firmlink 卷，`/Users` 与 `/System/Volumes/Data/Users` 的 `(st_dev, st_ino)` 完全相同（`os.path.samefile()` 为 True）。限定范围实测 **168 150 个重复目录 / 19 178 个硬链接重复文件**（共 700 012 个文件） | 目录按 `(st_dev, st_ino)` 去重，且去重在**主线程**完成（不是 worker），配合层序 BFS 保证保留的是浅层路径，结果稳定不闪烁。文件**不**去重（硬链接应按路径逐条列出） |
| **表观大小 ≠ 实际占用** | 994.61 GB 的磁盘报出 **1896.45 GB**（比值 2.29）。稀疏文件是元凶：`Docker.raw` 表观 994.61 GB / 实际 14.52 GB；Xcode `CompilationCache` v8.data 17.18 GB / 0 B；v8.index 8.59 GB / 0 B | 新增 `_disk_bytes()`：Windows 用 `st_size`，其余平台用 `st_blocks * 512`。全盘扫描 851.63 GB vs `os_used` 831.29 GB（比值 1.024，差额为 APFS 元数据 / 快照 / 目录块），且 `sum(children) == root` 精确成立 |
| **SQLite 开销主导耗时** | `/Applications`（92 578 目录 / 657 180 文件）旧实现 19.36 s；profile 显示 1 120 076 次 `execute`（3.16 s）+ 1 504 次 `commit`（3.15 s）+ 277 733 次 `get_by_path`（0.81 s） | 见下 |

**新算法**：层序（level-synchronous）BFS + `ThreadPoolExecutor`（`_SCAN_WORKERS = 4`），
每个层级的目录并行 `stat`，结果回到主线程合并进按 BFS 序索引的内存数组
（父下标恒小于子下标）；文件与目录共用一个 id 计数器；行按 `_DB_BATCH_ROWS = 8000`
批量 `executemany` 写入，提交按时间节流到 ≤1 次/秒；第二阶段汇总只需
`range(len(dir_id)-1, 0, -1)` 反向遍历，**不再需要按路径深度排序**。
`pool.map` 的 `chunksize` 按线程数缩放以限制 Future 数量。

**实测**（macOS / APFS / 缓存已热）：

| 场景 | 旧 | 新 |
|---|---|---|
| `/Applications` 92 578 目录 / 657 180 文件 | 19.36 s | **9.7 s**（≈2.0×，已等于纯遍历下限 9.68 s） |
| `/Users` 247 018 目录 / 1 547 120 文件 | — | 34.2 s，654.70 GB vs `du` 651.90 GB（比值 1.004） |
| 全盘 `/` 773 852 目录 / 3 446 384 文件 | — | **76.8 s**，851.63 GB |

线程数取 4 是实测结论：纯遍历 4 线程 5.17 s、8 线程 8.41 s、16 线程 10.79 s —— 更多
线程会被 GIL 争用与随机读放大吃掉。

**跨平台**：`ui/space_index_page.py` 的 `_get_available_drives()` 三个分支分别处理
Windows（`GetLogicalDrives` + `GetDriveTypeW`）、macOS（`/` + `/Volumes/*` 挂载点）、
Linux（`/` + `psutil.disk_partitions()` 真实挂载点，并过滤 squashfs/tmpfs/overlay 等
伪文件系统）—— 此前 Linux 只返回 `/`，外接盘完全扫不到。树视图列名由「大小」改为
「占用」，与访达「占用空间」、资源管理器「磁盘上的大小」同口径。

**已知限制**：Python 在 Windows 上不暴露 `st_blocks`，因此 Windows 的稀疏文件仍按
表观大小计入（需 `GetCompressedFileSize` 才能修正），已在文档中标注。

### 16.3 联机房间（功能补全）

直连房间此前**只有界面没有链路**，四个缺陷叠加导致「房间里什么都没有」：

| 缺陷 | 后果 | 处理 |
|---|---|---|
| `RoomSession` 是死代码（从未被实例化） | 客户端从不发心跳 → 房主在 `HEARTBEAT_TIMEOUT`(10 s) 后剔除全部成员，人数掉回 1 | 新增 `RoomSessionWorker`（QThread）承载 `RoomSession`；首次心跳立即发送，之后每 3 s 一次，分片睡眠保证 `stop()` 及时 |
| `RoomPage.update_peers()` 从未被调用 | 「在线成员」永远只显示房主 | 房主侧由 `RoomHostWorker.roster_updated`（500 ms 轮询 `build_roster()`）推送；加入者由心跳 ack 携带的 `roster` 推送 |
| `VoiceWorker` 没有暴露 `set_peers()` | 语音线程把音频发往**空列表**，界面却显示「语音已连接」 | `VoiceWorker` 新增 `set_peers()`，`RoomPage` 在成员变化时同步；`start()` 之前先设置，避免开头几百毫秒丢音频 |
| 房间内**没有任何文件传输** | 只有「局域网传输」页能传文件 | `RoomPage` 新增「发送给」（全部成员 / 指定成员）+「发送文件」+ 进度条，直接复用已加固的 `network/transfer.py` |

**房间文件传输端口**：新增 `utils.constants.room_data_port_for_room(room_port)`
（12800–13199，默认端口 12345 → **13160**），推导时跳过 12345 / 12346 / 12347 /
`room_port` / `room_port+1` / 该房间的语音端口，避免与任何既有端口相撞。进入房间即
开始监听该端口，所有成员共用同一个值；房主在 `MSG_ROOM_JOIN_ACCEPT` 里显式下发。

**成员名单**：`RoomHost.build_roster()` 返回 `[{peer_id, username, ip, is_host}]`，房主在首位。
**名单里绝不包含 `session_id`** —— 它是房主签发的会话凭证，泄漏给同房间其他成员即可
冒充他人。名单搭载在既有的 3 秒心跳 ack 与 `MSG_ROOM_JOIN_ACCEPT` 上，不新增长连接。

**会话失效**：房主不认识某个 `session_id` 时回 `known: False`，客户端停止心跳并提示
「会话已失效，请重新加入房间」。**不做静默重注册** —— 那会让房间口令对局域网嗅探者
失去意义。

**昵称统一**：房间成员名改用 `settings.username`（`RoomLobbyPage._username()`），
此前用 `socket.gethostname()`，会显示成 `xxxdeMacBook-Air.local`，与「局域网传输」页
的称呼不一致。

**实测验证**（回环，真实协议 + 真实 worker）：

- 房主建房间 → 客户端 A 加入（名单 2 人）→ 客户端 B 加入 → A 的心跳回包带来 3 人名单；
- **持续 13 秒后房主名单仍是 3 人**（原缺陷会在 10 秒掉回 1）；
- 伪造 `session_id` → 正确触发 `session_lost`；
- 成员 → 房主传 2 MiB 随机文件，SHA-256 一致；3 MiB 直传同样一致。

直连探测把「对端主机」交给了用户手填的地址，因此对端完全可能不是本程序 ——
下列都是**可被局域网触发的真实缺陷**，不是理论风险：

- **值也要当敌意输入**：`room_id` 只做「是否非空」判断，伪造主机回一个列表，
  客户端的 `{room_id: info}` / `rid in room_store` 就会抛
  `TypeError: unhashable type` —— Qt 槽里未捕获的异常会让进程直接 abort。
  现由 `_clean_room_id()` / `_clean_int()` / `_clean_text()` / `_clean_roster()`
  在协议边界归一化，UI 侧再兜一层。
- **会话凭证绝不外泄**：`build_roster()` 原以 `info.get("peer_id") or sid` 兜底，
  客户端只要上报空 `peer_id`，房主就把 **session_id 当 peer_id 广播给全房间**，
  同房间任何人都能冒名顶替。现改为不可逆派生值 `_fallback_peer_id()`，
  加入时也先做 `_clean_text()`。
- **探测不比广播多说一个字**：`_build_probe_reply()` 去掉 `data_port`，
  与 UDP 广播公告严格同为 8 项；验证脚本断言「探测字段 ⊆ 广播公告字段」。
- **探测可被真正取消**：原来 `RoomProbeWorker.cancel()` 形同虚设（阻塞 connect
  最长 5s）。现连接阶段改为非阻塞 connect + `select` 分片等待并轮询取消回调，
  大厅「取消/离开」可立即生效（实测 < 0.1s）。
- **主机自报 IP 不再覆盖用户填写地址**：多网卡机器上 `_get_local_ip()` 可能是
  另一个网段，会导致「探测成功但加入失败」；现在 `host_ip` 一律回填用户填的、
  刚刚连通验证过的地址。
- **无法查询 ≠ 通过**：`_count_audio_devices()` 返回 `-1` 时诊断项改为
  `warning`（原来报「可用，-1 个音频设备」）；打包版（`sys.frozen`）的
  「安装音频后端」修复改为如实说明内置后端、不再假装调用 pip。

## 18. 本次更新记录（v4.18.1：联机测试暴露的缺陷修复）

v4.18.0 重构完成后按「你可以测试，并根据测试结果优化完善」的要求做了两轮
**对抗性 + 不变量**测试（新增 `code/tools/fuzz_multiplayer.py`，并把关键回归
固化进 `verify_multiplayer.py`）。以下每一条都是实测复现过的缺陷，不是代码审查
的猜测；括号内为回归检查位置。按版本规则属**缺陷修复**，故只递增补丁位
（4.18.0 → 4.18.1）。

### 18.1 段错误：语音退出时崩溃（BLOCKER，exit 139）

实测：`VoiceClient.start()` 后**不调用 `stop()`** 直接退出，或 `start()` 后立刻
`stop()`，进程都以 `Segmentation fault: 11` 结束；而「等 0.6s 再停」则正常 ——
说明是**时序竞态**而非稳定错误：

- `start()` 只**同步**打开输出流；输入流是在 `_capture_loop` 线程里**异步**打开的
  （macOS 首次还要等麦克风授权，`Pa_OpenStream` 可能几百毫秒）。若在 `stop()`
  之后才打开完成，这条流就成了**没人管的孤儿流**，直到解释器退出才被 GC ——
  PortAudio 的流在解释器终结阶段才被释放，进程必崩。
- 反过来，`stop()` 在采集/播放线程仍阻塞于 `read()`/`write()` 时直接 `close()`，
  主线程与工作线程并发操作同一条 PortAudio 流，也是未定义行为。
- 从未 `stop()` 时连**普通 `atexit` 回调都还没执行**进程就崩了：崩溃发生在
  「解释器开始终结线程」阶段，早于 `atexit`。

修复（`network/voice_protocol.py`）：

| 措施 | 说明 |
|---|---|
| `stop()` 顺序 | 置位 → `abort()`（解除阻塞中的 read/write）→ `join(timeout)` → 关流 → 释放后端；幂等、可从任意线程调用 |
| 流的所有权 | 工作线程负责关闭**自己打开的**流（`finally`）；`stop()` 只在 join 超时后兜底补关 |
| 防重复关闭 | 新基类 `_StreamCloser` 用 `WeakSet` 记录已关闭的流 |
| 退出兜底 | `threading._register_atexit(stop_all_clients)` —— 它在**解释器终结线程之前**运行，也早于 `sounddevice` 自己的 `Pa_Terminate()`（顺序反了就是在已终止的 PortAudio 上 `abort`） |
| 测试性 | 新增 `_BACKENDS` 注册表 + `_make_backend()`，测试可注入「打开设备慢 400ms」的假后端，把竞态窗口变成**确定性**断言 |

回归：`verify_multiplayer.py` 的「语音关闭: …」5 项（假后端，不需要音频硬件）+
`--audio` 的「启动后不 stop() 也干净退出（无段错误）」（用子进程断言 exit code）。

### 18.2 畸形 JSON 报文可让监听线程静默死亡（MAJOR）

`[1,2,3]` / `5` / `"x"` / `null` 都是**合法 JSON 但不是对象**。四处解析点直接
`msg.get(...)`，抛出的 `AttributeError` 不在 `except (OSError, JSONDecodeError)` 之列，
于是**逃出监听循环**：

| 位置 | 后果 |
|---|---|
| `RoomHost._broadcast_loop` | 房主广播线程永久退出：房间还在，但所有人再也扫不到它（`_running` 仍为 True，无任何重启机制）——**局域网内 5 字节即可触发** |
| `RoomDiscoveryClient.scan` / `reply_listener` | 一次扫描/监听整体失败 |
| `DiscoveryService._listen_loop`（`_parse_msg`） | 设备发现监听线程永久死亡（局域网传输页再也发现不了设备） |
| `transfer._recv_header`（`ping_host`、加入/探测应答） | `ping_host` 抛栈；`probe_room` / `join_room` 抛 `AttributeError` 而非如实报错 |

修复：

- `transfer._recv_header()` 契约收紧为「**dict 或 None**」，非对象一律
  `ValueError("协议错误: 包头不是 JSON 对象（list）")`；`ping_host` 捕获并如实返回；
  `send_files` 去掉死分支；`receive_files` 保留二道防线。
- `room_protocol` 的 `scan()` / `reply_listener()` / `_broadcast_loop()` 三处
  `isinstance(msg, dict)` 后才使用。
- `discovery._parse_msg()` 只返回 dict/None（三个调用点一次性覆盖）。
- `probe_room` / `join_room` 的 ValueError 文案去重（不再出现「协议错误: 协议错误:」）。

回归：`verify_multiplayer.py` 4 项「非 JSON 对象」（探测/加入/ping_host/`_recv_header`）
+ 2 项「畸形 UDP 之后循环仍存活且仍能发现房间」；`fuzz_multiplayer.py` C/D 节。

> 关键教训：断言「没抛异常」是**假绿**。真正的判据是「畸形包之后循环还能继续工作」——
> 所以回归检查在注入畸形包**之后**再发一个合法公告，并要求它仍被发现。

### 18.3 测试工具本身的缺陷（同样修掉，避免假绿）

- `verify_multiplayer` 新增检查最初把伪主机绑在 `room_port` 上，而客户端连的是
  `room_port + 1` —— 测到的其实是 `Connection refused`。现改为绑 `+1`，并断言失败
  原因必须含「协议错误」。
- `fuzz_multiplayer` 的心跳伪主机首包分流错误（心跳连接的**首包就是** `MSG_HEARTBEAT`），
  导致「畸形名单」断言在 0 条数据上通过（假绿）。修正后要求「确实见过非空名单」。
- 畸形名单用例改为 500 条（可通过 64KB 包头上限）→ 真正覆盖「名单截断到 64 条」。
- 人数上限用例把 `max_players` 提到 64：20 轮会话在 10s 心跳超时窗口内会同时留在
  房主名单里，8 人上限会把「测试自身累积」误判为 `room_full`。
- **两个测试脚本不可并行运行**（都要占 UDP 12347）：并行时会出现「广播发现失败」的假红。

### 18.4 已知限制（未修改，附理由）

- **语音端口只有 400 个槽位**（`12400 + (room_port * 8) % 400`，6.5 万个房间端口必然
  共用；实测某端口最多被 1311 个房间端口共用）。隔离依赖「只单播给本房间名单里的 IP」；
  跨房间串音仅在「同一台机器同时加入两个语音端口相撞的房间」时可能出现。用「仅接受
  名单内 IP 的音频」可彻底隔离，但那会在多网卡机器上（TCP 记录 IP 与 UDP 出口 IP 不同）
  静默丢掉正常语音 —— 风险大于收益，故保持现状并记录。
- 房间端口恰在 12400–12799 区间时，`voice_port_for_room(p)` 可能等于 `p`（实测仅
  `p=12400`）或 `p + 1`（仅 `p=12743`）。`room_port` 本身在联机路径里从不 bind，
  且语音是 UDP、加入服务是 TCP，端口空间独立，无实际冲突。
- `voice_port_for_room()` 对非法入参（`0`/`None`/`"abc"`/`[1]`）不抛异常而是回落到
  区间内端口。调用方（`RoomJoinClient._join_target`）已先校验端口，故保持「宽松推导」。

### 19.1 定位与参考功能对照

**反向代理（reverse proxy）** 与"正向代理/抓包"不同：它在本机开一个**固定入口**
（如 `127.0.0.1:8888`），把收到的请求转发到**预先配置好的上游**（如
`https://api.example.com`），并把上游应答原样回给客户端。用途是：客户端里的
硬编码域名/端口不方便改（手机 App、写死了 `https://api.xxx.com` 的 SDK、只能在
真机跑的联调环境），把入口地址换成本机代理即可**不改代码**地观察、改写流量。

Reqable / Charles / mitmproxy(reverse) 的反向代理通常具备：网关映射规则（监听→目标）、
HTTP/HTTPS 双向、WebSocket、路径与请求头改写、HTTPS 证书（拦截或终止）、访问日志与
流量统计。本项目按下列对照实现，**不引入 MITM 证书拦截**（那需要全平台安装根证书，
属于安全敏感行为，见 19.6 限制）：

| 参考产品的能力 | 本项目实现 |
|---|---|
| 网关规则：监听地址 → 目标地址 | ✅ 多规则、多监听器，热增删 |
| HTTP/1.1 转发（含 chunked、大文件流式） | ✅ 流式转发，不整包缓冲 |
| HTTPS 上游（含自签/忽略校验开关） | ✅ 上游 TLS + `verify_tls` 开关 + SNI |
| HTTPS 入口（客户端 → 代理走 TLS） | ✅ 监听侧 TLS 终止（用户提供证书，或一键生成自签证书） |
| WebSocket | ✅ `Upgrade` 握手透传 + 101 后原始双向隧道 |
| CONNECT 隧道 | ✅ 仅允许连到**该规则的上游**，其它目标 403（不做开放代理） |
| 路径改写 | ✅ `strip_prefix`（去掉入口前缀）+ `add_prefix`（追加前缀） |
| 请求/响应头改写 | ✅ 规则内键值表，值置空 = 删除该头 |
| Host 改写 / X-Forwarded-* | ✅ 默认改写 Host；补 `X-Forwarded-For/Proto/Host`、`Via` |
| 重定向 Location 回写 | ✅ 默认把上游自身 origin 改回入口 origin（可关） |
| 访问日志 + 统计 | ✅ 环形日志（UI 实时刷新）+ 请求/错误/流量/连接数 |
| 断点/改包/重放（MITM 拦截） | ❌ 不做（见 19.6） |
| HTTP/2、HTTP/3 | ❌ 不做（ALPN 强制 http/1.1，见 19.6） |

### 19.2 规则模型（`ProxyRule`，JSON 存储）

存储位置：`%APPDATA%/LIWENTool/proxy_rules.json`（macOS
`~/Library/Application Support/LIWENTool/`，Linux `$XDG_DATA_HOME/LIWENTool/`），
经 `utils.jsonstore` 原子写入；读写由 `utils/proxy_store.py` 负责。

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | str | 自动 `r` + 8 hex | 主键，缺失时自动生成 |
| `name` | str | `""` | 显示名（可为空，界面回退显示监听地址） |
| `enabled` | bool | `true` | 关掉的规则不监听 |
| `listen_host` | str | `127.0.0.1` | 监听地址；填 `0.0.0.0` 可让局域网设备接入（界面需提示风险） |
| `listen_port` | int | `8888` | 监听端口，1–65535；**拒绝 12345/12346/12347**（本应用自身端口） |
| `match_host` | str | `""` | 按请求 `Host` 头分发；留空 = 该端口的**兜底规则**。支持精确域名与 `*.example.com` 通配 |
| `upstream` | str | 必填 | 上游基址，如 `https://api.example.com` / `http://127.0.0.1:9000/base` |
| `strip_prefix` | str | `""` | 入口路径前缀，命中则从转发路径中删除（不命中则原样保留） |
| `add_prefix` | str | `""` | 转发前往路径前追加 |
| `host_header` | str | `""` | 非空则用它作 `Host`，否则自动用上游 `host[:port]` |
| `rewrite_location` | bool | `true` | 响应 `Location` 指向上游 origin 时改回入口 origin |
| `verify_tls` | bool | `true` | 上游 HTTPS 是否校验证书（自签上游需关） |
| `connect_timeout` | float | `10.0` | 连接上游超时（0.5–600） |
| `read_timeout` | float | `60.0` | 上游读写超时（0.5–600） |
| `allow_connect` | bool | `true` | 是否允许 `CONNECT`（仅限上游 host:port） |
| `tls_cert` / `tls_key` | str | `""` | 监听侧 TLS 证书/私钥 PEM；**两者必须同时给**，启动时校验文件存在 |
| `request_headers` | dict[str,str] | `{}` | 转发前写入请求头；**值为空串 = 删除该头** |
| `response_headers` | dict[str,str] | `{}` | 回给客户端前写入响应头；同上 |

校验入口 `normalize_rule(raw)`：非 dict → `RuleError`；关键字段类型/取值非法 → `RuleError`
（**不静默补默认值放行**）；未知键丢弃；头名必须是合法 token，头值不得含 `CR/LF`
（防头注入）；`tls_cert`/`tls_key` 只给其一 → `RuleError`；`match_host` 只接受域名
（含 `*.` 前缀），带协议/路径/空格一律 `RuleError`。

**同一监听端口上可以挂多条规则**（按 `Host` 分发，见 19.4 第 12 条），此时组合本身也要合法，
由 `validate_groups()` 在启动/热更新时校验，违反则 `ProxyStartError`：

| 组合约束 | 违反时的中文原因 |
|---|---|
| 同一 `listen_host:listen_port` 至多一条 `match_host=""` 的兜底规则 | 「端口 N 只能有一条不限 Host 的兜底规则（已被规则「X」占用）」 |
| 同一端口上 `match_host` 不得重复（忽略大小写与结尾点） | 「端口 N 上 match_host=… 已被规则「X」占用」 |
| 同一端口上多条规则的 `tls_cert`/`tls_key` 必须一致（一个端口只有一份 TLS 配置） | 「端口 N 上的多条规则必须使用相同的入口证书」 |

> 端口相同但 `listen_host` 不同（如 `127.0.0.1:8888` 与 `0.0.0.0:8888`）视为**两个入口**，
> 不共享监听器；`0.0.0.0` 与 `127.0.0.1` 同时监听同一端口在部分平台上会绑定失败，
> 此时按「端口被占用」如实报错。

### 19.4 转发语义（实现必须遵守）

1. **只支持 HTTP/1.1**：解析 `请求行 + 头`（上限 `MAX_HEAD_BYTES`/`MAX_HEADERS`/`MAX_REQUEST_LINE`）；
   上游 TLS 用 ALPN 固定 `http/1.1`。
2. **边界即拒绝**（对齐 CLAUDE.md 不变量 6/11）：
   - 请求行非法/头块畸形 → `400`；头块超长或头数超限 → `431`；
   - `Content-Length` 非数字/负数 → `400`；
   - **同时出现 `Content-Length` 与 `Transfer-Encoding` → `400`**（请求走私防护）；
   - `chunk-size` 非十六进制/超上限 → `400`；
   - 客户端断开/超时 → 关闭连接，不留线程。
3. **hop-by-hop 剥离**：`Connection`、`Proxy-Connection`、`Keep-Alive`、`TE`、`Trailer`、
   `Transfer-Encoding`、`Upgrade`、`Proxy-Authorization`、`Proxy-Authenticate`；
   **`Connection` 头里点名的自定义头一并剥离**。升级请求例外：`Connection: Upgrade` +
   `Upgrade` + `Sec-WebSocket-*` 原样转发。
4. **入口头补全**：`Host` → 上游 `host[:port]`（或 `host_header`）；`X-Forwarded-For` 追加
   （保留客户端原值）；`X-Forwarded-Proto`（客户端是否 TLS）；`X-Forwarded-Host`（客户端原
   Host）；`Via: 1.1 LIWENTool`。
5. **路径映射**：`path = add_prefix + (path 去掉 strip_prefix) + "?" + query`（query 原样）。
6. **body 流式**：`Content-Length` / `chunked` 两种请求体按块转发（不整包读入内存）；
   `Expect: 100-continue` 由代理回 `100 Continue` 后再转发 body。
7. **响应**：透传状态行与头（剥离 hop-by-hop、应用 `response_headers`）；1xx 透传；
   `101` 之后进入**原始双向隧道**（WebSocket）；`204/304` 与 `HEAD` **不得等待响应体**；
   无 `Content-Length` 且非 chunked 的响应读到 EOF 并关闭（HTTP/1.0 上游）。
8. **错误语义**：上游连不上/TLS 校验失败 → `502`；上游读超时 → `504`；`CONNECT` 目标不是
   本规则上游 → `403`；并发超 `MAX_CONNECTIONS` → `503`。错误响应体是一行中文原因，同时写日志。
9. **keep-alive**：客户端与上游各自独立维持；任一侧要求 `Connection: close` 即关闭该侧。
10. **`stop()`**：关闭所有监听套接字 → 唤醒并关闭活动连接 → `join(timeout)`；
    幂等；返回仍存活的线程数（>0 要记日志，绝不 `terminate()`）。
11. **无 Qt、无 requests**：核心层可被 CLI 与测试脚本直接使用；日志走 `utils.logger`
    （`function_scope` 记录启停）。

12. **同一端口的 Host 路由**：请求按 `Host` 头（`CONNECT` 用 `authority`）选规则，
    顺序为 **精确匹配 → 通配（`*.example.com`，取最长键、只吃一级标签）→ 兜底规则**；
    匹配时忽略大小写、端口与结尾点。兜底规则 = `match_host=""` 的那条；若该端口
    **只有一条**规则，则它就是兜底（单规则端口不会因为 Host 不匹配而失败）；
    若有多条 Host 规则且都不匹配、又没有兜底 → `404 Not Found` 并在正文说明原因。
    命中哪条规则，`upstream`/`strip_prefix`/`add_prefix`/`host_header`/头改写/统计
    与访问日志就全部按该条规则执行；上游连接**不跨规则复用**（规则切换即重建连接）。
    `CONNECT` 只能打到**选中规则**的上游，其余目标仍是 `403`。

### 19.6 已知限制（有意不做，且必须在文档与界面里如实说明）

- **不做 MITM 证书拦截**：要解密客户端发往真实域名的 HTTPS，必须在客户端设备安装根证书，
  属于高风险的中间人行为。本功能只做「终止入口 TLS（自签证书需客户端信任）」与
  「上游 TLS 透传」，**不解密**第三方 TLS 流量。
- **不做 HTTP/2 / HTTP/3**：上游与客户端都按 HTTP/1.1 处理（ALPN 强制 http/1.1）。
  HTTP/2 客户端连接会被降级或拒绝（`400`），不谎报支持。
- **不做开放代理**：`CONNECT` 只允许连到规则配置的上游；监听地址默认 `127.0.0.1`，
  改成 `0.0.0.0` 时界面提示"局域网内任何设备都可通过本机代理访问该上游"。
- **不做请求体/响应体的断点改写与重放**（无 MITM 便无改包能力）；日志只记元数据
  （方法/路径/状态/耗时/字节数/错误），不落盘请求内容，避免记录用户凭据。

### 19.8 实现记录（实现期发现并修复的真实缺陷）

写文档时以为是「照抄一份转发逻辑」，实际动手后暴露了 9 个必须记下来的问题。
第 1–4、7 项是被测试抓出来的**产品缺陷**，第 5 项是**平台语义坑**，第 6 项是**测试自身的假红**，第 8 项是**路由语义的静默错投**。

1. **chunked 响应挂死（自查发现）**：`Transfer-Encoding` 属于 hop-by-hop，最初被无条件剥离，
   于是上游发来的分块响应只有分帧、没有分块声明，客户端一直等 `0

`，直到超时。
   修法：`_build_response_head(..., chunked=True)` 在透传分帧时**重新发出**
   `Transfer-Encoding: chunked`（请求方向同理）。**规则：剥 hop-by-hop 是「不转发对手给的」，
   不是「不声明自己要发什么」。**
2. **裸 CR / 裸 LF 头注入（fuzz 抓到）**：解析前只按 `\r\n` 归一化，`X-A: 1\rX-B: 2` 这种
   头里的单个 CR 会留在值里被原样转发，而下游实现对齐方式各不相同（正是头注入/走私的温床）。
   修法：`\r\n` 归一化后仍存在单独 `\r` 或 `\n` → `400`。这比 RFC 允许的更严格，是故意的。
3. **重复 `Content-Length` 未校验（fuzz 抓到）**：`_hget` 只取第一个值，`CL: 5` + `CL: 6`
   被当成 `5` 转发，上游却可能用另一个值 —— 经典请求走私。修法：值有冲突 → `400`；
   值相同的重复则去重后只发一个。
4. **规则热删留下僵尸线程（自查 + 压测抓到）**：`remove_rule()` 关闭了监听器与登记过的连接
   socket，但 macOS 上对已进入 CLOSE_WAIT 的连接 `shutdown()` 会抛 `ENOTCONN`，
   随后的 `close()` **并不会唤醒已经阻塞在 `recv()` 里的线程** —— 线程永不退出，
   `stop()` 报 `leaked_threads: 1`。修法：不再依赖「关 fd 唤醒阻塞读」，而是给每个监听器
   一个 `closed` 事件，空闲等待改成 **0.5 s 分片 `select` 轮询** `self._stop` / `listener.closed`，
   同时把上游 socket 也纳入 `_active` 统一关闭。**规则：跨平台收线程只能靠"能被轮询的状态位"，
   不能靠"关 socket 会让阻塞调用抛异常"这种 BSD 与 Linux 不一致的实现细节。**
5. **平台语义坑（写测试时必须知道）**：「`stop()` 后端口能否重新绑定」不能裸 `bind()` 判断 ——
   刚服务过连接的端口会留下 `TIME_WAIT`，裸 bind 必然 `EADDRINUSE`，那是 TCP 语义不是泄漏。
   正确判据：`SO_REUSEADDR` 后再 bind，或直接「用同一条规则重新 `start()` 成功」。
   `fuzz_multiplayer.py` C 节另有一处同类假红：假主机假设 `scan()` 会发出 ≥3 个探测包
   （实际只广播 2 次），畸形应答之后永远等不到第 3 个包，于是「畸形包之后仍能发现房间」
   必然失败 —— 改为畸形应答后**主动补发**合法公告，检查才真正测到「循环没被打断」。
6. **`ProxyRuleStore.update()` 曾复用 `add()`**：`add()` 是「移除后追加」，于是界面里编辑/启停
   一条规则会让它跳到表格末尾。改为原地覆盖（规则不存在时才追加），行序稳定。
7. **「一规则一监听器」→「一端口一监听器 + 路由表」的分组改造**（v6.0.0 追加 `match_host` 时）：
   把 `_Listener.rule` / `_Listener.target` 换成 `routes` 字典 + `pick()` 之后，`_accept_loop`
   里残留的一句 `rule = listener.rule` 让 accept 线程在**第一个连接**上就抛 `AttributeError`
   而死 —— socket 被 accept 了却永远没人处理，客户端只看到超时，应用日志里连一条错误都没有
   （线程死在了 `threading` 的兜底打印里）。**教训：把「单值属性」换成「集合 + 选择器」时，
   必须全局搜索该属性的每一处引用**。验证套件在改动后第一次运行就抓到了（第 2 节整节变红），
   否则这就是最难排查的一类故障：端口开着、连接能建、就是没响应。
8. **同端口 Host 路由的兜底语义（自查发现）**：最初 `default_rule()` 无条件回落到「路由表里的
   第一条」，于是「一个端口全是 Host 规则且都不匹配」时请求会被**静默发给任意一条规则** ——
   错投到生产上游比报错危险得多。现语义：显式 `match_host=""` 优先；**只有一条规则**时它就是
   兜底（单规则端口不因 Host 不匹配而失败，保持老行为）；多条 Host 规则且都不匹配 → `404`
   并在正文说明「没有匹配 Host 的规则」。回归检查：验证套件第 16 节 16 项。

9. **分组改造后的两处连带缺陷（自查发现）**：
   (a) `stats()` 里 `"listening": rule["id"] in self._listeners` —— 监听器改成按
   `(host, port)` 分组后，这个判据**恒为 False**，界面上每条规则都会显示成"未监听"，
   而端口其实好好地在服务。改为逐监听器查路由表（`_rule_listening()`）。
   **教训：容器的键换了，所有 `in` 判据都要跟着换**。
   (b) 无匹配 Host 的 `404` 原本只 `warn()` 到 `data/log.txt`，不进访问日志 ——
   界面上"日志一片正常"而客户端在吃 404，正是最难自查的情形。现在记为
   **无归属事件**（`rule_id=""`，`error` 里写明原因）：总请求/错误数计入，
   按规则细分不受污染，界面日志的「规则」列显示为 `—`。

另外三处**规格细化**（写文档时留白、实现时必须定下来）：

- **`100-continue`**：客户端带 `Expect: 100-continue` 时，代理**自己**先回 `100 Continue`，
  再把请求头与 body 转发给上游 —— 不做这件事，客户端会一直等 interim 响应而卡死。
- **`CONNECT` 的授权判据**是 `host:port` 与规则上游（含默认端口推导）精确匹配，其余一律
  `403` + 中文原因；**绝不**变成开放代理。
- **入口 TLS 的 `X-Forwarded-Proto`**：TLS 终止时值为 `https`（否则 `http`），
  这是上游区分协议的唯一可靠信号，已由验证套件断言。
